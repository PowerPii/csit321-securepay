# Contracts

The only code-level things shared between services. Start with [`API-CONTRACT.md`](API-CONTRACT.md): the merchant API rules (idempotency, signatures, errors, webhook retries, guest status) for milestone M2. The gateway-to-simulator rules (operation IDs, status queries, "no record", fault controls) are in [`SIMULATOR-CONTRACT.md`](SIMULATOR-CONTRACT.md). v2 splits the simulator into acquirer, switch and issuer: [`NETWORK-CONTRACT.md`](NETWORK-CONTRACT.md).

- `openapi/merchant-api.v1.yaml` and `openapi/guest-status.v1.yaml` are the design-first contracts (OpenAPI 3.1). `gateway.yaml` will be generated by drf-spectacular (`python manage.py spectacular --file ../contracts/openapi/gateway.yaml`) once the endpoints exist and must agree with them. `simulator.yaml` is design-first too, for the gateway-to-simulator API.
- `schemas/` holds the shared objects as JSON Schema 2020-12: Payment, Refund, the webhook Event envelope and Error. The OpenAPI files reference them.
- `events/` holds one JSON Schema per merchant notification: `payment.verification_required`, `payment.processing`, `payment.authorised`, `payment.declined`, `payment.blocked`, `payment.unresolved`, `payment.captured`, `payment.cancelled`, `payment.expired`, `refund.completed`, `refund.failed`, `refund.unresolved`. Each carries an event ID, a per-payment sequence number and a snapshot of the object; the signature header carries the timestamp.
- `examples/` holds example payloads. `python contracts/check.py` (run in CI) validates the schemas, the OpenAPI files and every example, and checks that payment statuses match `gateway/apps/payments/states.py`.
- `generated/` holds TypeScript types generated from the OpenAPI files for the frontends.

Do not share the payment state-machine code between the gateway and the simulator, so independent tests can catch a defect in either.
